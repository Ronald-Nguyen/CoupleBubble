# AGENTS.md – Operational Guidelines & Architecture Standards

This document defines operational rules, architectural constraints, and quality standards for AI agents working on the **CoupleBubble** codebase.

---

## 1. Core Operating Directives

### Documentation Synchronization
- **Mandatory Update Rule:** Whenever an architectural decision is made, a new screen or model is added, or the tech stack/dependencies change, both `README.md` and `AGENTS.md` must be updated within the same task or commit.
- Never leave discrepancies between the documented architecture and the actual codebase.

### Scope Control & Minimal Blast Radius
- Modify only the files strictly required to accomplish the specific prompt or task.
- Do not reformat untouched files or reorganize directory structures without explicit instruction.
- Remove all dead code, temporary debug variables, and unused logging statements before marking a task complete.

### Dependency Governance
- All dependencies must be managed strictly inside `gradle/libs.versions.toml` (Gradle Version Catalog).
- Never hardcode library versions inside `app/build.gradle.kts` or module-level build scripts.
- Do not introduce new third-party libraries without explicit user confirmation.

### Committing
- **Commit Without Asking:** Once `./gradlew assembleDebug` and `./gradlew testDebugUnitTest` pass, commit the task's changes right away without asking for confirmation, using the commit message given in the task.
- **Batch Runs:** When a task is run by `run_features.ps1` or `run_features_agy.ps1` (its system prompt says so), do not commit or rewrite git history; the script builds, tests, lints and commits itself, and asks for fixes with the build errors if the build fails.
- **One Commit, No Splitting:** If uncommitted changes from earlier tasks are still in the working tree, commit everything together (`git add .`) instead of splitting it into separate commits.

## 2. UI/UX & Design Standards ("Anti-AI-Slop")

The UI must feel human, intimate, tactile, and custom-tailored for couples. Generic AI SaaS templates and clichés are strictly prohibited.

### Prohibited UI Patterns
- **No Generic Purple/Indigo Gradients:** Do NOT use `#6366f1`, `#8b5cf6`, or neon glow borders.
- **No Gimmicky Decorative Icons:** No sparkle icons (`✨`), magic wands (`🪄`), or heart badges enclosed in random floating circular backgrounds.
- **No Generic AI Marketing Copy:** Avoid clichés like "AI-driven love" or "Empower your relationship". Use authentic, warm German microcopy.
- **No Excessive Card Nesting:** Maximum one card layer. Structure inner content via whitespace, typography scale, subtle dividers, and tonal surface shifts.
- **No Unnecessary Subtitles or Descriptions:** Leave out subtitles, taglines and explanatory sub-texts under headings (e.g. "Einkaufszettel, Reiseideen, alles, was ihr teilen wollt." under "Notizen") when the title and content already speak for themselves.
- **No Automatic Center-Alignment:** Use natural, left-aligned editorial layouts with intentional white space.

### Mandatory Design Tokens & Styling Rules
- **Color Palette (Material 3):**
  - **Primary:** Deep Navy Blue (`#0F2137` / Dark: `#97CBFF`)
  - **Secondary / Accent:** Sunset Orange / Terracotta (`#E65D2E` / Dark: `#FF8A65`)
  - **Surfaces:** Deep Navy-tinted containers (`#162B48`). Never use pitch-black OLED black (`#000000`) for cards or dialogs.
- **Depth & Borders:** Use crisp 1px borders (`BorderStroke(1.dp, Color.White.copy(alpha = 0.08f))`) and tonal elevation rather than heavy, blurred ambient shadows.
- **Micro-Interactions & Haptics:** Apply `LocalHapticFeedback.current` on key touchpoints (copying pairing codes, milestone triggers, date submissions, emotional check-ins). Primary actions use `HapticFeedbackType.LongPress`, fired only once the action is confirmed: successful gallery downloads, copying the pairing code (only if the clipboard service accepted it), saving a new or edited moment (via `CoupleEffect.MemorySaved`, sent only after the repository saved it), saving a reunion, swapping partner roles, deleting a note (editor menu or the selection bar's bin, fired on the tap since undo replaces the confirmation), confirming a custom milestone deletion, clearing checked list items. Light selection changes use `HapticFeedbackType.TextHandleMove` (pairing tab switch, bottom-navigation tab switch, notes label filter, accent-color palette pick, date changes in `MemoryDatePickerDialog`, the reunion location switch, a moment's milestone checkbox, a note's label, pin toggle, text ↔ checklist conversion, checking a list item, a checklist item swapping places while dragged), and only when the selection actually changes.
- **Touch Targets (min. 48 dp):** Every clickable element gets at least a 48×48 dp hit area (`MinTouchTarget` in `ui/components/TouchTarget.kt`); the visible shape may stay smaller. `IconButton`s keep their default size (never shrink them with `.size(< 48.dp)`), small circular visuals (color swatches, header avatars) use `Modifier.circularTouchTarget(visualSize)`, small clickable rows/chips get `heightIn(min = MinTouchTarget)` or a 48 dp wrapper box, and gesture handles (checklist `DragIndicator`) take `size(MinTouchTarget)` around the 24 dp icon. Palettes that cannot fit 48 dp cells in one row wrap with `FlowRow`.
- **Large Font Scales (200 %):** Containers holding text never get a fixed height; use `heightIn(min = …)` (PIN boxes, 54 dp buttons, chips) and no fixed `lineHeight` overrides. Hero numbers and the header's space name use `maxLines = 1` + `TextOverflow.Ellipsis`; the generated pairing code may wrap. No text below the theme's `bodySmall` size or with reduced alpha for readable content. Pairing, dashboard and notes have `fontScale = 2f` previews, rendered by `PreviewSmokeTest`.
- **Physics-Based Motion:** Use `spring()` animations (e.g., `spring(stiffness = Spring.StiffnessLow)`) for scaling and state transitions. Avoid linear animations. **Reduced motion:** `LocalReducedMotion` (`ui/components/ReducedMotion.kt`) is provided by `MainActivity` from `Settings.Global.ANIMATOR_DURATION_SCALE == 0` (`isReducedMotion`, observed live via a `ContentObserver`, since the setting changes without a configuration change); endless animations (the pulsing heart in `SpaceTopHeader`, the pulsing countdown icon in `CreateCodeTab`) then render static, one-time spring transitions stay. New endless animations must check it too.
- **Typographic Contrast:** Hero counter numbers must be large (`48.sp` to `56.sp`, `FontWeight.ExtraBold`), paired with small, tracked uppercase labels (`12.sp`, `letterSpacing = 1.5.sp`).
- **Consistent Dialog Buttons:** Confirm/apply actions on the right as a filled `Button` (secondary/primary, or `colorScheme.error` for destructive actions such as deleting or discarding changes), dismiss actions on the left as a `TextButton` („Abbrechen“, or „Schließen“ for close-only dialogs like Google-Sicherung or milestone settings). Dialogs do not duplicate `onDismiss()` calls when the action already closes the dialog.

## 3. Localization & Strings

- **Zero Hardcoded User-Facing Strings:** All display texts, button labels, content descriptions, and dialog messages must reside in `app/src/main/res/values/strings.xml`.
- **Tone:** UI strings must be written in natural, warm, personal German ("Du" form, empathetic, clear).
- **Documentation Language:** `README.md`, `AGENTS.md`, `PRIVACY_POLICY.md`, code comments and KDoc are English; only user-facing strings (`strings.xml`) are German.

Tests mirror these packages; fakes live in `src/test/.../data/fake/`.
- **Platform:** Native Android (Kotlin DSL, `minSdk = 26`, `targetSdk = 36` or latest)
- **Splash Screen & Window Theme:** `androidx.core:core-splashscreen` (`Theme.CoupleBubble.Starting` with Deep Navy `#0F2137` background, app icon `@mipmap/ic_launcher`, and `postSplashScreenTheme="@style/Theme.CoupleBubble"`). `MainActivity.onCreate()` installs the splash screen before `super.onCreate` and configures `setKeepOnScreenCondition` (`SplashKeepOnScreenCondition`) until session restoration completes (`container.sessionRestorer.isRestored.value`) or a sensible timeout (3 s) is reached, seamlessly replacing the startup loading spinner without a color flash ("Farbblitz"). The base window theme is DayNight-capable (`Theme.CoupleBubble` in `values/` with parent `android:Theme.Material.Light.NoActionBar` and `@color/window_background_light` `#FBF8F4`, in `values-night/` with parent `android:Theme.Material.NoActionBar` and `@color/window_background_dark` `#0F151B`).
- **UI Framework:** Jetpack Compose with Material 3 (`androidx.compose.material3`)
- **Homescreen Widget:** Jetpack Glance with Material 3 (`androidx.glance:glance-appwidget`, `androidx.glance:glance-material3`)
- **Architecture:** MVVM with Unidirectional Data Flow (UDF)
- **State Handling:** `StateFlow` backed by immutable UI state objects (`sealed interface` / `data class`)
- **Local Persistence:** Jetpack DataStore Preferences (`androidx.datastore:datastore-preferences`)
- **Image Loading & Handling:** Coil for Compose (`io.coil-kt:coil-compose`) with custom components registered in `CoupleBubbleApplication` (`ImageLoaderFactory`): `Base64Mapper` (maps `String` → `Base64Image`), `Base64Keyer` (generates memory cache keys `"b64:${length}:${hashCode}"` for zero redundant decoding), and `Base64Fetcher` (decodes `Base64Image` directly into `BitmapDrawable` via `DrawableResult` to ensure zero stream exhaustion issues in Coil's `BitmapFactoryDecoder`). Because Coil executes mappers before fetchers, `Base64Mapper` runs ahead of the built-in `StringMapper` to intercept Base64 data and raw payloads before Coil can convert them into unhandled `android.net.Uri` instances. Handles remote `https://` URLs, local `file://` / `content://` URIs, data URIs (`data:image/...`), and raw Base64 image payloads (`/9j`, `iVBORw0KGgo`, `UklGR`) seamlessly across all devices and partners with automatic `file:///9j` healing. Moments support dual photos (Partner 1 & Partner 2) stacked vertically, held in `Memory.partner1ImageUrl` / `partner2ImageUrl` and stored in the Firestore fields `partnerAImageUrl` / `partnerBImageUrl` (all field names live in `data/remote/FirestoreSchema.kt`; Kotlin names use 1/2, stored names keep their legacy A/B spelling). Every upload gets a unique Storage name (`{memoryId}_{slot}_{uid}_{epochMillis}.jpg`, profiles `profile_{uid}_{epochMillis}.jpg`) and local files are versioned the same way, so a role swap can never make one partner overwrite the file the other partner's URL points to, and Coil never serves a stale cached image. The legacy `imageUrl` field is read-only: it is only used as A's photo for old single-photo moments (when B is empty), is deleted on every update/swap, and an A slot equal to B is treated as a duplicate (`resolveMemorySlots` in `FirestoreSchema.kt`). Memory photos utilize Local-First persistence (`LocalImageStore.saveMemoryImage`) for immediate 0ms rendering and offline resilience, followed by background Firebase Storage upload with a 10s timeout, falling back to compressed Base64 data URIs so partner devices never receive inaccessible local sandbox `file:///` URIs. Image compression (`LocalImageStore.compress` (`AndroidLocalImageStore`)) automatically corrects EXIF rotation and applies adaptive compression guaranteeing payloads stay under 250 KB to ensure multi-photo Firestore documents never breach the 1MB document limit. Image URLs are sanitized via `ImageUrls.sanitize` (`data/local/ImageUrls.kt`, which also owns the Base64 signature table, `healFileBase64`, `isLocalUri` and `jpegDataUri`) with raw Base64 normalization. Exporting/downloading photos to the device gallery is handled via `LocalImageStore.saveToGallery` supporting Base64, local files, and remote URLs using `MediaStore.Images.Media` (`Pictures/CoupleBubble`) with Scoped Storage support (Android 10+ without prompts, and API 26-28 fallback). Fullscreen modal viewer supports multi-touch pinch-to-zoom (1f–4f), double-tap zoom (1f <-> 2.5f), bounded pan translation, direct gallery downloads, and swipe-to-dismiss: at normal zoom (`scale <= 1.05f`) a single-finger vertical drag moves the photo (`dragOffsetY`), fades the black backdrop (`alpha = (1f - |dragOffsetY| / 600f).coerceIn(0.2f, 1f)`), closes the viewer with a spring exit beyond 150 dp, and springs back to `0f` below it; multi-touch gestures and zoomed-in pans stay with the transform detector. The memory card menu action "In Galerie speichern" exports all photos of a moment (Partner A and B, de-duplicated). A collapsed memory card shows a 28 dp `MemoryPreviewThumbnail` of its first photo, framed by a 1.5 dp border in its owner's accent color. Memory cards default to expanded so photos remain immediately discoverable in the timeline. Each photo slot in a memory card (`MemoryPhotoSlot`) is framed by a `BorderStroke(1.5.dp)` in the owner's accent color (`partner1ColorHex` / `partner2ColorHex`); the partner's slot shows a subtle 14 dp `Icons.Default.Lock` in its top-right corner to signal it is read-only for the current user. Upload status: `DashboardViewModel` (via `MemoryPhotoUploadTracker.track`) keeps the local-first copy of an added/edited memory in `_pendingMemories` (overlaid on the Firestore list by id) and marks every slot receiving new bytes as `PhotoSyncState.UPLOADING` in `DashboardUiState.photoSyncStates` (keyed by `PhotoSlotKey(memoryId, isPartner1)`); add/edit dialogs close right away. When the repository returns, slots with an `https://` Storage URL switch to `SYNCED` for 1.5 s, while Base64 fallbacks and failures just drop the state. `PhotoSyncBadge` (bottom-right of `MemoryPhotoSlot`, black 45 % pill with 1px border) shows spinner + `Icons.Default.CloudUpload` while uploading, a check mark when synced, and fades out with `spring` animations. The dashboard `Scaffold` hosts an `ExtendedFloatingActionButton` (`Icons.Default.Add`, `colorScheme.secondary` Terracotta) that fires a short haptic tick and emits `DashboardEvent.ShowAddMemoryDialog(true)`; it collapses to icon-only via `derivedStateOf` once the content is scrolled (`firstVisibleItemIndex == 0 && firstVisibleItemScrollOffset < 120`). `DashboardScreen` uses a `LazyColumn` with stable keys (`header`, `invite_partner`, `together_card`, `reunion`, `empty_timeline`, `year_$year`, `bottom_spacer`); year groups and memory card expansion states persist across configuration changes and tab switches via `rememberSaveable`. **Search in moments & fast year jump:** A search icon in `SpaceTopHeader` (`memories_search_button`) toggles an inline search bar (`BasicTextField`, auto-focus, clear, and close buttons; `DashboardEvent.OpenSearch`, `CloseSearch`, `SearchQueryChanged`). Pure function `filterMemories` (`domain/model/MemoryFilter.kt`) filters memories across title, personal note, year, and German month names (case- and umlaut-tolerant). In search mode, hero cards are hidden for focus, a hit count is displayed (`memories_search_count`), and empty results show `EmptySearchTimelineCard` (`memories_search_empty`); Android Back or the back arrow closes search. When moments span multiple years (`years.size > 1`), `TimelineYearJumpRow` renders horizontal chips (`year_chip_$year`) allowing smooth-scrolling (`animateScrollToItem`) directly to the corresponding year header. Long-pressing a memory card opens the same options menu as the three-dot button (via `combinedClickable` with `onLongClickLabel` set to `memory_options`). Re-tapping the active bottom navigation tab (`PairedHomeScreen.onTabReselected`) smoothly scrolls the screen (`LazyListState` in dashboard, `LazyStaggeredGridState` in notes) back to the top. **Deleting moments (undo instead of confirmation):** the card menu emits `DashboardEvent.DeleteMemory` without a dialog; `DashboardViewModel` hides the moment at once (`_hiddenMemoryIds`, filtered out of the timeline), keeps it as the one `pendingDeletion` and sends `CoupleEffect.Snackbar` with a `SnackbarAction` („Rückgängig“, `UndoDeleteMemory` / `CommitDeleteMemory`). `MainActivity` shows snackbars with an action as `SnackbarDuration.Long` and sends `onActionPerformed` or `onDismissed` back according to the `SnackbarResult`; `SnackbarAction<E>` is generic over the event type, so `MainActivity` dispatches `DashboardEvent`s to `DashboardViewModel` and `NotesEvent`s to `NotesViewModel` (an `onDismissed` of `null` does nothing). The same `SnackbarHostState` serves the notes tab. Only the commit calls `deleteMemory`, in the container's `AppContainer.appScope` (not `viewModelScope`); a pending deletion is committed at once when a second deletion arrives or in `onCleared`. A failed delete un-hides the moment and shows `memory_delete_failed`. An empty timeline renders a single Terracotta-bordered card containing only a centered "Ersten Moment eintragen" button (`Icons.Default.Add`) that opens the same add-memory dialog. In add/edit memory dialogs (`MemoryFormDialog`, `editableRole: PartnerRole?`), users can only modify their own photo slot; with an unknown slot both stay read-only, and the partner's empty slot is hidden (no placeholder). The timeline's „Foto ergänzen“ button only appears for the current user's own missing photo. The dialog only reports `OwnPhotoEdit` (Keep / Remove / Replace(uri)) for the own slot, and the repository API `addMemory` / `updateMemory(coupleId, memory, fallbackRole, ownPhoto: MemoryPhotoChange)` writes title/date/note plus, for a photo change, only the slot resolved from the auth UID inside a `runTransaction` that reads the space and the stored memory (the partner's slot is taken from the server copy, never from the client). Text-only edits merge only the text fields, so they cannot overwrite a concurrent partner photo. Without a slot the photo change is dropped with `memory_photo_slot_unknown` and only the text is saved. The lock icon in `MemoryPhotoSlot` follows `currentUserRole`. A role swap is refused while a memory photo upload is pending (`_pendingMemories`), since the swap reads the memory list before its transaction. Avatar rings gracefully fall back to partner initials via `onError` in `PhotoAvatarWithRing`. All `ImageRequest` instances in Compose are wrapped with `remember(url)` to prevent recomposition loops.
- **Layering & UDF wiring:** `AppContainer` (interface in `core/di/`, production `DefaultAppContainer` created lazily in `CoupleBubbleApplication`) holds one instance per process of every collaborator (`FirebaseProvider` with the lazy Firestore/Auth/Storage entry points and the offline cache settings, `RemoteImageUploader` for Storage uploads with the Base64 fallback, `FirebaseSpaceRepository` / `FirebaseMemoryRepository` / `FirebaseMilestoneRepository` combined by delegation into `FirebaseCoupleRepository`, `FirebaseNotesRepository`, `FirebaseReunionRepository`, `AndroidLocationProvider`, `AndroidConnectivityObserver`, `DataStoreSessionStore`, `AndroidLocalImageStore`, `GoogleAuthClient`, notifier, widget publisher) plus `AppDispatchers` (main/io/default, injected instead of `Dispatchers.*`) and builds the ViewModels; ViewModels only see the interfaces `CoupleRepository`, `SessionStore`, `LocalImageStore` and `GoogleSignInClient` and never call `FirebaseAuth`/`FirebaseApp` themselves (`CoupleRepository.ensureSignedIn` / `currentAuthUid`). `PairingScreen` and `DashboardScreen` take a state plus `onEvent` (`PairingEvent` / `DashboardEvent` in `ui/screens/home/CoupleEvents.kt`, dispatched by `PairingViewModel.onEvent` / `DashboardViewModel.onEvent`). One-shot feedback (toasts, snackbars, the haptic confirmations after a role swap, a saved moment or a gallery export) is sent as `CoupleEffect` through `PairingViewModel.effects` / `DashboardViewModel.effects` / `SettingsViewModel.effects` and shown once by `MainActivity`, which also owns the `SnackbarHostState` passed to `DashboardScreen`. Composables do no file I/O (`ProfilePhotoCropDialog` decodes through `LocalBitmapLoader`, provided by `MainActivity` from `LocalImageStore.loadSampledBitmap`): photo compression (`AddMemory`/`UpdateMemory` carry picked `Uri`s) and gallery export (`SaveToGallery`, progress in `DashboardDialogState.isSavingToGallery`) run in the ViewModel via `LocalImageStore`. User-facing texts produced by ViewModels are `UiText` (string or plural resource; there is no raw variant, exception messages are never shown, unknown errors map to a resource such as `pairing_connection_failed`); repository exceptions are the sealed `CoupleException` family in `domain/error/` (`InvalidPairingCodeException`, `SpaceUnavailableException`, `SpaceFullException`, `PartnerNotConnectedException`, `PartnerSlotUnknownException`; `findCause` unwraps them from transaction errors) and mapped to resources in the ViewModel. `CoupleRepository` is the union of `SpaceRepository`, `MemoryRepository` and `MilestoneRepository`. Firestore documents are converted only in `data/remote/mapper/` (`SpaceMapper`, `UserMapper`, `MemoryMapper`, `MilestoneMapper`, `NoteMapper`), which work on plain `Map`s (`DocumentSnapshot.fields()`) so they are unit-tested without Firebase; every field name comes from `FirestoreSchema`, collection references from `FirestoreRefs.kt`. `DashboardUiState` embeds `DashboardDialogState` (`dialogs`: tab, menu, busy flags and the one open `DashboardDialog`, a sealed type so two dialogs can never be open at once; the custom-milestone dialog is `MilestoneSettings(addingCustom = true)` and its delete confirmation `MilestoneSettings(deletingCustom = …)` on top of the settings) and the shared `GoogleAuthState`. UI state classes are `@Immutable`; `app/compose_stability.conf` marks the domain models, `LocalDate` and Kotlin collections as stable for the Compose compiler. Placeholder defaults (names, colors, anniversary) live only in `domain/model/SpaceDefaults.kt`; the stored partner-role preference is read through `PartnerRole`. UI files: `ui/screens/dashboard/` (DashboardScreen, SpaceTopHeader, TogetherCard, ReunionCard, ReunionDialog, MilestoneDialogs, MemoryTimeline, MemoryFormDialog for adding and editing, EditNamesDialog, FullscreenImageViewer), `ui/screens/pairing/` (PairingScreen, CreateCodeTab, EnterCodeTab, SpaceFullDialog), `ui/screens/settings/` (SettingsScreen, SettingsViewModel, SettingsUiState, SettingsEvent), shared pieces in `ui/components/` (SpaceSetupDialog, GoogleAuthCard, MemoryDatePickerDialog, DiscardChangesDialog, ValidatedTextField). Mock repositories live in `src/test` only.
- **Honest Feedback:** Success messages come from the ViewModel only after the repository `Result` succeeded, never from the click in a composable: `DashboardEvent.AddMemory` / `UpdateMemory` end in `CoupleEffect.MemorySaved` (`memory_added` / `memory_updated`, LongPress haptic in `MainActivity`), `DashboardEvent.SavePartnerDetails` (names plus changed colors in one event) ends in `names_and_colors_updated`. While `DashboardViewModel.isOnline` is false (from `ConnectivityObserver`), both success messages become `saved_offline` („Gespeichert – wird synchronisiert, sobald du online bist“), since Firestore only wrote its offline cache. Every repository `Result` is evaluated; a failure shows a snackbar with warm German text that says what to do (`names_save_failed`, `space_setup_save_failed` (dialog stays open), `memory_save_failed`, `milestone_save_failed`, `milestone_delete_failed`, `reunion_save_failed`, `reunion_place_save_failed`, `reunion_delete_failed`; in notes `note_create_failed` (closes the new note's editor), `note_save_failed`, `note_delete_failed` (the notes show up again), `note_labels_save_failed`). Debounced note text writes report at most one snackbar per failing series (`NotesViewModel.textWritesFailing`, reset by the next successful write); writes to a note the partner deleted meanwhile stay silent. Background writes (the hourly reunion location refresh, deleting an `Over` reunion) stay silent. Fakes `MockCoupleRepository.failWrites` / `MockNotesRepository.failWrites` simulate refused writes in tests.
- **Backend:** Firebase (Authentication with Google SSO / Credential Manager, Cloud Firestore with Offline-Cache, Cloud Storage) operating on Spark Free Tier.
- **Room Membership & Limitation:** Spaces are strictly limited to exactly 2 participants (`userUids.size <= 2` / `members.size <= 2`). `connectWithCode` validates client- and backend-side to prevent unauthorized 3rd-party joining (`SpaceMapper.isJoinRefused`, unit-tested; the joined space is mapped by `SpaceMapper.joined` + `fromFields`, the same mapping as the listener); a full space fails with the typed `SpaceFullException`, which `PairingViewModel` (`PairingEvent.Connect`) maps to `PairingUiState.showSpaceFullDialog` instead of an inline error. `SpaceFullDialog` in `PairingScreen` offers "Code erneut prüfen" (`onRecheckCodeAfterSpaceFull`: closes the dialog, clears the PIN) and "Eigenen Raum erstellen" (`onCreateOwnSpaceAfterSpaceFull`: clears the PIN, switches to the CREATE tab and generates a fresh code). Documented Security Rule: `allow update: if request.auth != null && (resource.data.members.size() < 2 || request.auth.uid in resource.data.members);`.
- **Profile Accent Colors & Avatars:** Individual hex colors (`partner1ColorHex`, `partner2ColorHex`) customizable via 8 curated couple palette colors or any custom color via `CustomColorPickerDialog` (supporting HSV sliders, live avatar ring preview, and direct Hex input). Text and icons drawn on a surface filled with a partner color (avatar initials, palette check marks, picker preview) use `getContrastingTextColor` (`ui/theme/Color.kt`): `ColorUtils.calculateLuminance` > 0.45 returns `ContrastNavy` (`#0F172A`), otherwise `Color.White`. Fallback initials sit on a solid accent-color fill. Only one's own profile photo can be edited by each partner, and the slot is never passed in from the UI: `uploadProfilePhoto(coupleId, fallbackRole, bytes)` resolves it from the auth UID (`CoupleSpace.editableRole` in `domain/model/PartnerRole.kt`) and writes it inside a `runTransaction` against the server's `partner1Id` / `partner2Id`, so a role swap during the upload cannot put the photo into the partner's slot (offline it falls back to a merge into the locally resolved slot). `fallbackRole` (the stored preference) only counts in a space without members (demo). `DashboardUiState.currentUserRole` is `null` while the UID is not bound; then both avatars show `profile_photo_slot_unknown` instead of guessing, and an unbound or unknown slot fails with the typed `PartnerSlotUnknownException`. Swap and profile-photo upload exclude each other (`DashboardDialogState.isSwappingRoles` / `isUploadingProfilePhoto`). Local profile copies are named after the owner's UID, not the slot. Tapping an avatar with a photo opens it in `FullscreenImageViewer` (zoom, download, swipe-to-dismiss): the partner's avatar opens directly, one's own avatar shows a small menu ("Im Vollbild ansehen" / "Foto ändern"); without a photo the own avatar opens the picker as before. Profile photo selection includes interactive circular cropping (`ProfilePhotoCropDialog`) with pan and zoom gestures and zoom slider. Avatars use Local-First caching (`LocalImageStore.saveProfilePhoto`) for 0ms immediate UI display, followed by background Firebase Storage upload with a strict 10s timeout and Base64 Data URI fallback (`data:image/jpeg;base64,...`) written unconditionally to Firestore so changes immediately sync across all devices via snapshot listeners even if storage permissions or network fail.
- **Pairing Codes:** Codes are 6 random digits, displayed as `482-913` and stored without the hyphen (`space_482913`, `pairingCode`). `connectWithCode` rejects anything that is not exactly 6 digits. ## 5. Jetpack Compose & State Rules

- **Unidirectional Data Flow (UDF):** Composables accept state objects (`uiState: MyUiState`) and emit lambda events (`onEvent: (MyUiEvent) -> Unit`). Never inject ViewModels into leaf composables.
- **Preview Coverage:** Every screen and shared component must include at least one `@Preview` composable wrapped in `CoupleBubbleTheme` and populated with realistic mock data (supporting both Light and Dark mode previews). Shared sample data lives in `ui/preview/PreviewData.kt`; `PreviewSmokeTest` renders the non-dialog previews under Robolectric.
- **Logic Separation:** Zero business calculations, Firebase operations, or network requests inside Composable functions.
- **Performance Hygiene:** Never instantiate heavy objects inside Composable bodies without wrapping them in `remember`. Use `derivedStateOf` for calculated properties dependent on changing state.
- **Accessibility:** All clickable elements without text must have meaningful `contentDescription` string resources. TalkBack semantics (helpers in `ui/components/Accessibility.kt`, tested in `AccessibilityTest`, `PairingSemanticsTest`, `TimelineSemanticsTest`, `NotesSemanticsTest`):
  - Section labels, year headers and dialog titles get `semantics { heading() }`.
  - Status and error texts that change on their own get a `liveRegion`: PIN error (`pairing_error`, Assertive), code countdown (`code_countdown`, Polite, speaks whole minutes via `minutesLeft` / `code_valid_minutes` instead of a seconds ticker), photo upload badge (Polite).
  - Expandable elements (year groups, memory cards) use `Role.Button` plus `stateDescription` from `expansionStateDescription(expanded)` („ausgeklappt“ / „eingeklappt“); their arrow icons have no own description.
  - Header avatars read „Profilbild von {Name}“ with an `onClickLabel` matching the action (`avatar_action_view` / `_options` / `_pick`; `circularTouchTarget` takes `onClickLabel`).
  - Color swatches (`CouplePalette` in `ui/components/CouplePalette.kt`, shared by `EditNamesDialog` and `CustomColorPickerDialog`) read their color name with `Role.RadioButton` and `selected`; the HSV sliders carry their caption as `contentDescription`.
  - Codes are spelled digit by digit (`spokenDigits`): the PIN field's `stateDescription` is „3 von 6 Ziffern eingegeben: 4, 8, 2“, the generated code reads „Dein Kopplungscode: 4, 8, 2, 9, 1, 3“.
  - Checklist rows in the note editor are one merged node (`Role.Checkbox`, item text as `contentDescription`, `toggleableState`, double tap toggles); checkbox, drag handle and delete button are cleared from the tree, the text field stays its own node so it remains editable. Open items offer `customActions` „Nach oben verschieben“ / „Nach unten verschieben“ (`ChecklistReorderState.move` → `NotesEvent.ReorderItems`) as an alternative to drag and drop, every item „Löschen“.
  - Note cards read one summary (`noteCardSummary`: title, „Etikett {Name}“, progress, „Angeheftet“, „Neue Änderungen“, „Erstellt von {Name}“; the author dot has no own node) instead of each text; label filter chips set `selected`.

## 6. Security, Secrets & Zero-Cost Firebase Guardrails

### Secrets Lockdown
- Never commit, edit, or expose: `release.jks`, `key.properties`, `google-services.json`, or environment configuration files.
- Keep all credentials, API keys, aliases, and passwords out of Git history.

### Firebase Spark Plan Constraints & Optimization
- **Prevent Firestore Read/Write Loops:** Avoid continuous polling. Rely on snapshot listeners (`addSnapshotListener`) with lifecycle-aware cleanup (`callbackFlow` / `awaitClose`) or single fetch operations.
- **Atomic Operations:** Use Firestore transactions or WriteBatches during pairing/unpairing to prevent orphaned partner documents.
- **Client-Side Image Compression:** Compress images client-side before uploading to Firebase Storage via `LocalImageStore.compress` (`AndroidLocalImageStore`) (target resolution max 1200px, quality 80% JPEG, file size under 400 KB).
- **Offline Resilience:** Rely on Firestore offline persistence for immediate UI rendering while syncing in the background.
- **Listener Errors Keep State:** Snapshot listeners never emit an empty list (or `null` labels) on error; they keep the last state, since an empty list would look like a deletion (closed note editor, partner-moment notifications for every old moment).
- **One Listener per Collection:** `SpaceContent` keys the memory, custom-milestone and reunion listeners on the space id and shares them (`shareIn`) between the timeline, notifications, widgets and the milestone reminder.
- **Cancellation:** generic `catch (e: Exception)` around suspend calls must call `e.rethrowIfCancellation()` (`core/Cancellation.kt`) first.

### Google SSO & Release Signing Configuration
- **Web-Client-ID Auto-Resolution:** `default_web_client_id` is generated automatically from `google-services.json` by the Google Services Gradle plugin. Never place placeholder strings like `YOUR_GOOGLE_WEB_CLIENT_ID` in `strings.xml`, as Android resource merging prioritizes `strings.xml` over generated values and breaks Google Sign-In.
- **Rules in the Repository:** `firebase/firestore.rules` and `firebase/storage.rules` (wired in `firebase.json`) describe the access the app needs. They were reconstructed from the code; compare them with the Firebase console before deploying, and update them together with any new collection or access pattern. Deploying stays manual (`firebase deploy --only firestore:rules,storage`).
- **Release Build:** R8 shrinking and resource shrinking are on (`isMinifyEnabled`, `isShrinkResources`); Firestore data is mapped by hand (`data/remote/mapper/`), never via reflection-based `toObject`, so models need no keep rules. Java/Kotlin target 17.
- **CI:** `.github/workflows/android.yml` runs `assembleDebug testDebugUnitTest lintDebug` on pushes to `main` and on pull requests.
- **R8 / ProGuard Keep-Rules:** Reflection classes used by AndroidX Credential Manager (`androidx.credentials.**`), Google Identity (`com.google.android.libraries.identity.googleid.**`), and Firebase Auth (`com.google.firebase.auth.**`) must remain preserved in `app/proguard-rules.pro` to prevent reflection and obfuscation breakage in release builds.
- **Debug & Play App Signing SHA-1 Fingerprints:**
  - **Local Development / Testing:** The local debug keystore SHA-1 must be registered in the Firebase Console under Android Apps so Google Play Services authorizes sign-in.
  - **Release / Play Console:** When deploying via Google Play Console, Google re-signs the bundle with its own Play App Signing key. The SHA-1 fingerprint from Play Console (**Release > Setup > App integrity > Play App Signing key certificate**) must be added to the Firebase project settings under Android Apps.
- **OAuth Client Check:** `google-services.json` must contain an `oauth_client` with `client_type: 1` and a `certificate_hash` for every signing key (local debug, upload key, Play App Signing). If only the Web client (`client_type: 3`) is present, Credential Manager fails with code 10/16/28444 (mapped to `google_error_sha1_missing`). A missing Play App Signing SHA-1 breaks sign-in only in Play Store installs; after adding it, re-download `google-services.json`. Without `${rootDir}/debug.keystore`, debug builds are signed with `~/.android/debug.keystore`.
- **Anonymous → Google Linking:** `GoogleAuthClient.signIn` upgrades an anonymous Firebase user via `linkWithCredential` to preserve the UID and `/users/{uid}` anchor, falling back to `signInWithCredential` only on `FirebaseAuthUserCollisionException`.
- **Credential Manager Error Handling:** Distinguish `GetCredentialCancellationException` (silent user cancellation, debug-logged only) from genuine authentication failures, displaying user-friendly German error messages in toasts or snackbars. Errors are mapped by exception type (`NoCredentialException`, `GetCredentialException` with `[10]`/`[16]`, `FirebaseAuthException`, `FirebaseNetworkException`), never by loose substring matching. **Sign-out never leaves the space:** `GoogleSignInClient.signOut` only clears the Credential Manager state, never the Firebase user, because the UID is the space membership (a new UID could not rejoin a full space). `CoupleRepository.signOutUser` is a no-op while a space is active; unpaired it signs out and immediately signs in anonymously again. Inside the dashboard `GoogleAuthCard` gets `onSignOutGoogle = null` and shows no sign-out button.
